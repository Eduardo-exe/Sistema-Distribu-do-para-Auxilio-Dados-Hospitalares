	\section{Introdução e Visão Geral}
	% =========================================================================
	
	Em um hospital, os pacientes são monitorados o tempo todo, e cada monitor gera um fluxo constante de informações importantes: sinais vitais, alertas e ocorrências de emergência. Se tudo isso chega a um único servidor central, ele pode ficar sobrecarregado, responder mais devagar e, pior, se ele cair, o sistema inteiro para (o chamado \textit{Single Point of Failure}).
	
	Foi pensando nesse problema que nosso grupo construiu o \textbf{Sistema Distribuído para Auxílio de Dados Hospitalares}. O projeto tem finalidade acadêmica e didática, e nós o desenvolvemos aos poucos, em marcos evolutivos. Neste documento contamos como foram os dois primeiros:
	
	\begin{itemize}
		\item \textbf{Marco 1 — Simulação e Servidor Base:} lemos, pouco a pouco, a telemetria de um conjunto de dados hospitalar (\textit{dataset} do Kaggle), validamos cada mensagem em uma API RESTful (FastAPI), convertemos os tipos de dados e guardamos tudo em um banco local (SQLite).
		\item \textbf{Marco 2 — Balanceamento de Carga e Múltiplas Instâncias:} colocamos três instâncias do servidor para rodar ao mesmo tempo e criamos um Balanceador de Carga que distribui as requisições pelo algoritmo \textit{Round Robin}, de forma transparente para quem envia os dados e com identificação clara de qual servidor processou cada mensagem.
	\end{itemize}
	
	Todo o projeto foi escrito em Python (versão 3.10 ou superior). Procuramos manter o código claro, com as partes bem separadas e fácil de rodar em qualquer máquina.

	Os dados que usamos vêm de um arquivo CSV do Kaggle:
	\begin{center}
		\texttt{Synthetic\_patient-HealthCare-Monitoring\_dataset.csv}
	\end{center}
	Em vez de gerar números aleatórios durante a execução, preferimos trabalhar com telemetria já coletada, que deixa a simulação mais próxima da realidade.
	
	Ao explorarmos o arquivo, encontramos o seguinte:
	\begin{itemize}
		\item \textbf{Volume:} 60.000 registros clínicos (60.001 linhas, contando o cabeçalho).

	\subsection{O Produtor de Telemetria (\texttt{client/csv\_sender.py})}
	Esse script faz o papel de um monitor biomédico à beira do leito, enviando os dados dos pacientes. Ele faz o seguinte:
	\begin{enumerate}
		\item abre o arquivo CSV de forma segura, com \texttt{csv.DictReader};
		\item converte cada linha com a função \texttt{converter\_registro\_csv}, transformando os textos em números inteiros ou decimais;
		\item envia cada registro ao servidor por uma requisição HTTP \texttt{POST}, com o corpo em JSON;
		\item espera um intervalo configurável entre os envios (\texttt{time.sleep(intervalo)}), o que permite simular tanto em tempo real quanto de forma acelerada;
		\item trata falhas de conexão (\texttt{ConnectionError} e \texttt{Timeout}), para que um problema momentâneo na rede não derrube todo o processo.
	\end{enumerate}
	
	\subsection{O Servidor Base (\texttt{server/app.py})}
	O servidor foi feito com o \textbf{FastAPI}, um framework assíncrono, e oferece três rotas principais:
	\begin{itemize}
		\item \texttt{POST /dados}: recebe os dados do paciente já validados pelo modelo \texttt{DadosPaciente} (Pydantic). O servidor adiciona o \texttt{timestamp} da máquina e o seu identificador (\texttt{server\_id}), grava no banco e devolve HTTP 200 com o registro salvo.
		\item \texttt{GET /dados}: devolve os registros armazenados, com paginação pelos parâmetros \texttt{limit} e \texttt{offset}, o que evita sobrecarregar a memória quando há dezenas de milhares de linhas.
		\item \texttt{GET /dados/\{paciente\_id\}}: devolve o histórico de um paciente específico, ou HTTP 404 se ainda não houver medições dele.
	\end{itemize}
	
	\subsection{Onde os Dados Ficam Guardados (\texttt{server/database.py})}
	Para a persistência usamos o \textbf{SQLite3}. Cada instância do servidor cuida do seu próprio arquivo de banco e cria a tabela \texttt{dados\_pacientes} ao iniciar:
	
	\begin{lstlisting}[language=SQL, caption={Estrutura da Tabela no SQLite}]
		CREATE TABLE IF NOT EXISTS dados_pacientes (
		id INTEGER PRIMARY KEY AUTOINCREMENT,
		paciente_id INTEGER NOT NULL,
		frequencia_cardiaca INTEGER NOT NULL,
		spo2 INTEGER NOT NULL,
		pressao_sistolica INTEGER NOT NULL,
		pressao_diastolica INTEGER NOT NULL,
		temperatura REAL NOT NULL,
		deteccao_queda TEXT NOT NULL,
		doenca_prevista TEXT NOT NULL,
		precisao_dados INTEGER NOT NULL,
		alerta_freq_cardiaca TEXT NOT NULL,
		alerta_spo2 TEXT NOT NULL,
		alerta_pressao TEXT NOT NULL,
		alerta_temperatura TEXT NOT NULL,
		timestamp TEXT NOT NULL,
		server_id TEXT NOT NULL
		);
	\end{lstlisting}

	\subsection{O Algoritmo Round Robin}
	O \textbf{Round Robin} funciona como um revezamento: as requisições são entregues aos servidores um de cada vez, em ordem, e quando a lista acaba voltamos ao primeiro. Formalmente, dado um conjunto fixo de $N$ servidores $\mathcal{S} = \{s_0, s_1, \dots, s_{N-1}\}$ e um contador de requisições $r \in \mathbb{N}$ (que começa em 0):
	
	\begin{equation}
		\text{Servidor Alvo}(r) = s_{r \pmod N}
	\end{equation}
	
	Com essa regra, a carga se divide de forma igual entre os servidores:
	\begin{itemize}
		\item Requisição 1 ($r=0$): Servidor $0$ (\texttt{server-01}, porta 8001)
		\item Requisição 2 ($r=1$): Servidor $1$ (\texttt{server-02}, porta 8002)
		\item Requisição 3 ($r=2$): Servidor $2$ (\texttt{server-03}, porta 8003)
		\item Requisição 4 ($r=3$): Servidor $0$ (\texttt{server-01}, porta 8001)
	\end{itemize}
	
	Implementamos o balanceador na classe \texttt{RoundRobinBalancer}, no módulo \texttt{load\_balancer/balancer.py}, e usamos a biblioteca \texttt{httpx.AsyncClient} para encaminhar as requisições de forma assíncrona.
	
	\subsection{Como Cada Servidor se Identifica}
	As três instâncias rodam exatamente o mesmo código, mas cada uma recebe pela linha de comando a sua própria identidade e o seu próprio banco:
	\begin{itemize}
		\item \textbf{Instância 1:} porta \texttt{8001}, ID \texttt{"server-01"}, banco \texttt{databases/server1.db}
		\item \textbf{Instância 2:} porta \texttt{8002}, ID \texttt{"server-02"}, banco \texttt{databases/server2.db}
		\item \textbf{Instância 3:} porta \texttt{8003}, ID \texttt{"server-03"}, banco \texttt{databases/server3.db}
	\end{itemize}
	
	Quando o balanceador repassa a requisição e recebe a resposta do servidor escolhido, ele devolve ao cliente um HTTP 200 que traz o campo:
	\begin{center}
		\texttt{"server\_id": "server-01"}
	\end{center}
	Assim, o cliente consegue conferir em tempo real como a carga está sendo dividida, sem perder a \textit{transparência de localização}: ele continua falando somente com o endereço \texttt{http://localhost:8000}.
	
	\subsection{Bancos de Dados Independentes}
	Como definido no planejamento da disciplina, \textbf{ainda não implementamos replicação nem sincronização entre os bancos} nesta etapa.
	
	Cada servidor grava apenas no seu banco SQLite local (\texttt{server1.db}, \texttt{server2.db} ou \texttt{server3.db}). Por isso, se o balanceador enviar 12 registros, cada um dos 3 bancos guardará exatamente 4. A persistência distribuída consistente e a replicação entre os nós ficam para o Marco 3.

	\section{Decisões de Engenharia e Desafios Superados}
	% =========================================================================
	
	Ao longo dos Marcos 1 e 2 tomamos algumas decisões importantes, e algumas delas nasceram de problemas que encontramos pelo caminho:
	
	\begin{enumerate}
		\item \textbf{Troca de um recurso descontinuado do FastAPI:} as versões recentes do FastAPI deixaram de recomendar o decorador \texttt{@app.on\_event("startup")}. Passamos a usar o gerenciador de ciclo de vida assíncrono (\texttt{lifespan}) e chamamos \texttt{init\_db()} antecipadamente, de forma idempotente. Isso resolveu os erros de tabela inexistente nos testes com \texttt{TestClient}.
		\item \textbf{Respeito ao dataset original:} o CSV de 4,4 MB não foi copiado nem alterado. Criamos um \textit{symbolic link} (\texttt{data/dataset.csv}) apontando para o arquivo original, o que mantém tudo reproduzível sem gastar espaço extra.
		\item \textbf{Testes do Marco 2 sem conflito de portas:} ao testar servidores e balanceadores reais em segundo plano, reaproveitar portas TCP rapidamente causava o erro \texttt{Errno 98: Address already in use}. Resolvemos usando \textit{fixtures} de escopo de classe (\texttt{scope="class"}) no \texttt{pytest}, com portas dinâmicas na faixa 19000. Com isso, sumiram as condições de corrida e os travamentos.
	\end{enumerate}

	\section{Conclusão}
	% =========================================================================
	
	Os objetivos dos Marcos 1 e 2 foram alcançados, e o cronograma atualizado na Seção~\ref{sec:gantt} mostra que o projeto segue dentro do previsto. Com esse trabalho, conseguimos aplicar na prática conceitos importantes de Sistemas Distribuídos:
	\begin{itemize}
		\item heterogeneidade e acoplamento fraco entre os componentes, por meio do protocolo HTTP e do formato JSON;
		\item uso de dados reais de telemetria, sem precisar recorrer a dados sintéticos desnecessários;
		\item balanceamento de carga Round Robin com transparência de acesso e tolerância a falhas na camada do cliente;
		\item uma estrutura modular, que prepara o caminho para o Marco 3 (sincronização e replicação de dados).
	\end{itemize}
	
	Daqui para frente, nosso foco será o Marco 3, começando pela replicação dos dados entre os servidores, e depois a tolerância a falhas do Marco 4.
